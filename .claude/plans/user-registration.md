# ניהול רישום משתמשים — סגירת הרשמה עצמית + מסך הוספת משתמשים למנהלת

## Context

שתי דרישות:
1. **שרק משתמשים רשומים ייכנסו** — לא שכל אחד שמגיע לכתובת יוכל להירשם.
2. **שלמנהלת תהיה אפשרות לחבר משתמשים נוספים** מתוך המערכת, בלי להיכנס ל‑Supabase Studio.

בנוסף: **ללא עלות כספית**.

### מה קיים היום

- `Login.jsx` מבצע `signInWithPassword` בלבד. טופס ההרשמה הוסר בקומיט `aa34d25`.
- יצירת משתמש נעשית ידנית ב‑Supabase Studio. הטריגר `handle_new_user()` יוצר שורת `profiles` עם `role='user'` קשיח ו‑`full_name` מ‑`raw_user_meta_data`.
- שיוך תפקיד נעשה ידנית ב‑SQL Editor. `canManageUsers()` קיים ב‑`src/lib/permissions.js:75` (admin בלבד) אך **אינו בשימוש באף מקום**.
- `profiles` RLS: `select` פתוח לכל מחובר, `update` לשורה עצמית, אין policy ל‑insert/delete.

### הבעיה האמיתית שהתגלתה

**הסרת הטופס מהקוד לא סגרה את ההרשמה.** מפתח ה‑`anon` נמצא ב‑bundle הציבורי, ולכן כל אחד עדיין יכול לקרוא ישירות ל‑`POST /auth/v1/signup`, לקבל חשבון, ולזכות בשורת `profiles` אוטומטית מהטריגר. מכיוון שכל טבלה כמעט היא `select ... to authenticated using (true)`, הוא מקבל גישת קריאה כמעט לכל הנתונים.

הפרצה שקומיט `aa34d25` התכוון לסגור **עדיין פתוחה** — היא נסגרת רק ע"י כיבוי ההרשמה ברמת הפרויקט. זהו החלק הקריטי בתוכנית הזו, והוא שינוי הגדרה — לא קוד.

### שיקול העלות — הוא זה שקובע את העיצוב

| רכיב | עלות | מסקנה |
|---|---|---|
| Supabase Edge Functions | 500,000 קריאות/חודש חינם ב‑Free plan | חינמי לחלוטין בהיקף הזה (עשרות קריאות בשנה) |
| שליחת מייל הזמנה דרך Supabase | שירות המייל המובנה מוגבל ל‑2 מיילים לשעה, **ומסרב לשלוח לכתובות שאינן של חברי צוות הפרויקט** | **לא שמיש** ללא ספק SMTP חיצוני |

לכן: **משתמשים נוצרים עם סיסמה התחלתית שהמנהלת קובעת ומוסרת — בלי מייל בכלל.** זה עוקף את מגבלת ה‑SMTP, לא עולה כלום, ולא דורש ספק חיצוני.

---

## גישה

Edge Function אחת (`admin-users`) שמחזיקה את מפתח ה‑`service_role` בצד השרת, ומסך "משתמשים" באפליקציה שקורא אליה. שתי שכבות הרשאה כמתחייב מ‑CLAUDE.md: ה‑UI מסתיר, ו‑**ה‑Edge Function אוכפת** — ושם זו אכיפה אמיתית, לא רק הסתרה.

מפתח ה‑`service_role` **לעולם לא מגיע לדפדפן**. זו הסיבה היחידה שנדרש רכיב צד‑שרת.

---

## שלב 0 — כיבוי ההרשמה העצמית (חובה, קודם לכל השאר)

ב‑Supabase Dashboard → **Authentication → Sign In / Providers → Email**:
- לכבות **"Allow new users to sign up"**.

`auth.admin.createUser` ממשיך לעבוד גם כשההרשמה כבויה, כי הוא רץ עם `service_role` שעוקף את ההגבלה. אין התנגשות בין שלב 0 לשאר התוכנית.

**זהו השלב היחיד שמספק את דרישה 1.** אם עוצרים כאן — הדרישה הראשונה כבר מולאה.

## שלב 1 — Edge Function

קובץ חדש: `supabase/functions/admin-users/index.ts`

תיקיית `supabase/` מכילה כרגע רק `migrations/` — זו התוספת הראשונה של קוד צד‑שרת לריפו, ויש לציין זאת ב‑CLAUDE.md (ראה שלב 4).

הפונקציה:
1. מטפלת ב‑`OPTIONS` ומחזירה כותרות CORS (נקראת מהדפדפן ב‑domain של Cloudflare).
2. קוראת את ה‑JWT מכותרת `Authorization`, מזהה את המשתמש הקורא, וטוענת את `profiles.role` שלו.
3. **דוחה כל מי שאינו `admin`** ב‑403. אין להסתמך על שום דבר בגוף הבקשה כדי לזהות את הקורא.
4. לפי `action`:
   - `list` — מחזירה את כל שורות `profiles` (id, email, full_name, role, created_date).
   - `create` — `auth.admin.createUser({ email, password, email_confirm: true, user_metadata: { full_name } })`, ואז עדכון `profiles.role` לתפקיד שנבחר.
   - `set_role` — עדכון `profiles.role` למשתמש קיים.

הערות מימוש:
- `SUPABASE_URL` ו‑`SUPABASE_SERVICE_ROLE_KEY` מוזרקים אוטומטית לסביבת ההרצה של Edge Functions — אין להוסיף אותם ל‑`.env.local` ואין להתחייס אליהם בקוד הלקוח.
- `email_confirm: true` נחוץ כדי שהמשתמש יוכל להתחבר מיד בלי מייל אימות (שלא יישלח ממילא).
- **עדכון התפקיד**: הטריגר `protect_profile_role` חוסם שינוי `role` רק כאשר `auth.uid() is not null`. ל‑JWT של `service_role` אין claim בשם `sub`, ולכן `auth.uid()` הוא `null` והעדכון אמור לעבור. **זו נקודת הכשל הסבירה ביותר בתוכנית — יש לוודא אותה בפועל** (ראה אימות, שלב 2). אם התפקיד חוזר ל‑`user` בשקט, הפתרון הוא מיגרציה חדשה שמרחיבה את `handle_new_user()` לקרוא תפקיד מתוך `raw_user_meta_data`, במקום עדכון בדיעבד.
- אין צורך במיגרציה חדשה עבור התוכנית הזו — הסכימה הקיימת מספיקה.

פריסה: `npx supabase functions deploy admin-users` (דורש Supabase CLI, חינמי; זו הפעם הראשונה שהפרויקט משתמש ב‑CLI — עד היום המיגרציות הורצו ידנית ב‑SQL Editor).

## שלב 2 — מסך המשתמשים

קובץ חדש: `src/pages/Users.jsx`, בתבנית של דפים קיימים (`useEffect` + `useState`, בלי React Query — ראה CLAUDE.md).

- קורא ל‑Edge Function דרך ה‑client הקיים: `supabase.functions.invoke('admin-users', { body: { action, ... } })`. הוא מצרף אוטומטית את ה‑access token של המשתמש. משתמשים ב‑`supabase` המיוצא מ‑`src/api/base44Client.js` — לא ב‑shim `base44.entities`, שאינו יודע לקרוא לפונקציות.
- טבלת משתמשים: שם, אימייל, תפקיד (`getRoleDisplayName` מ‑`permissions.js`), תאריך יצירה.
- דיאלוג "הוספת משתמש": שם מלא, אימייל, סיסמה התחלתית, תפקיד (`ROLE_DISPLAY_NAMES` לתוויות). אחרי יצירה — הודעה ברורה שהסיסמה נמסרת למשתמש/ת ידנית.
- שינוי תפקיד למשתמש קיים דרך `Select` בשורה.
- הכל עטוף ב‑`canManageUsers(user)` — ההפעלה הראשונה של ה‑helper המת. עברית/RTL כמו שאר האפליקציה.

חיווט (שני מקומות, לפי CLAUDE.md):
- `src/App.jsx` — route `/users` בתוך `<Layout>`.
- `src/components/Layout.jsx` — פריט ניווט "משתמשים". `navItems` כרגע לא מסונן לפי תפקיד; להוסיף דגל `adminOnly` לפריט ולסנן מול ה‑`user` שכבר נטען שם, כדי שהפריט לא יוצג למי שלא יכול להשתמש בו.

## אימות

1. **שההרשמה סגורה** (הדרישה המרכזית): בדפדפן, מול הפרויקט,
   ```
   curl -X POST "$VITE_SUPABASE_URL/auth/v1/signup" -H "apikey: $VITE_SUPABASE_ANON_KEY" \
     -H "Content-Type: application/json" -d '{"email":"probe@example.com","password":"probe12345"}'
   ```
   לפני שלב 0 זה יצליח (וייצור משתמש — יש למחוק אותו). אחרי שלב 0 חייב לחזור שגיאת signup disabled. **זו הבדיקה שמוכיחה שדרישה 1 מולאה.**
2. **יצירת משתמש**: להתחבר כאדמין, ליצור משתמש בדיקה עם תפקיד `local_manager`.
3. **שהתפקיד באמת נשמר** (נקודת הכשל מסעיף 1): לרענן את המסך ולוודא שהתפקיד המוצג הוא `local_manager` ולא `עובדת ספרייה`. לאמת גם ב‑Studio מול `profiles`.
4. **התחברות**: להתנתק, להתחבר עם המשתמש החדש והסיסמה שנקבעה, לוודא שנכנס ושהשם מופיע באווטאר ב‑Sidebar (ולא `?`).
5. **שכבת ההרשאה בשרת**: להתחבר כמשתמש לא‑אדמין ולקרוא ידנית ל‑`supabase.functions.invoke('admin-users', { body: { action: 'list' } })` מה‑console. חייב לחזור 403 — זו ההוכחה שההגנה אינה רק הסתרת UI.
6. `npm run lint` — להשוות מול ה‑baseline האדום הקיים (~55 שגיאות), לא לצפות לירוק.
7. למחוק את משתמש הבדיקה ב‑Studio.

## מחוץ לגבולות

- **מחיקה/השבתה של משתמשים** מהמסך — לא נכלל. כרגע אין ל‑`profiles` policy ל‑delete בכלל. אפשר להוסיף בהמשך דרך אותה Edge Function.
- **"שכחתי סיסמה"** — לא נכלל. `resetPasswordForEmail` תלוי באותו שירות מייל מוגבל, ולכן דורש קודם ספק SMTP חיצוני. בינתיים איפוס סיסמה נעשה ע"י המנהלת (ניתן להוסיף `set_password` לאותה פונקציה).
- **הידוק `profiles` RLS** — כרגע כל מחובר יכול לקרוא את התפקידים של כולם. לא נדרש לצורך המשימה, אבל שווה בדיקה בעתיד.
- **יצירת משתמשים ב‑SQL בלבד** (בלי Edge Function) נשקלה ונדחתה: הכנסה ישירה ל‑`auth.users` עוקפת את GoTrue, שברירית מול שינויי סכימה, ועלולה לייצר משתמשים שבורים שאינם יכולים להתחבר.
